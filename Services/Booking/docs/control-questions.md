# Контрольні питання — короткі відповіді (на прикладі цього сервісу)

**1. З яких шарів складається тришарова архітектура і куди спрямовані залежності?**
Шари: Web/API → BLL → DAL; спільні моделі й винятки лежать у Domain. Залежності спрямовані в один бік: API знає лише сервіси BLL (`IBookingService`), BLL — лише абстракції DAL (`IUnitOfWork`, репозиторії). DAL не знає про HTTP, BLL не знає про SQL.

**2. Чому репозиторій повертає модель/DTO, а не SqlDataReader чи DataTable?**
Reader прив'язаний до відкритого з'єднання і до конкретної СУБД, а DataTable нетипізований. Якби вони виходили назовні, деталі SQL просочилися б у BLL. Модель (`Booking`, `Customer`) робить контракт типізованим, тестованим і незалежним від сховища.

**3. Навіщо Generic Repository і чому ADO.NET-репозиторій його не успадковує?**
Generic Repository дозволяє написати однаковий CRUD один раз (`BaseDapperRepository<T>`), а в конкретних репозиторіях лишити тільки специфічні запити. `CustomerRepository` його свідомо не успадковує:
- ключ клієнта — GUID, а не `long`;
- задача цього репозиторію — показати «ручний» ADO.NET: `SqlCommand`, `SqlParameter`, `SqlDataReader`, OUTPUT-параметр процедури.

**4. Чим відрізняється той самий запит через ADO.NET і через Dapper? Коли писати «руками»?**
- **ADO.NET:** команду, параметри з типами, цикл `ReadAsync` і мапінг кожного стовпця пишемо самі.
- **Dapper:** один виклик `QueryAsync<T>` з анонімним об'єктом параметрів; бібліотека сама створює команду й мапить рядки (через IL emit). З'єднання і транзакція — ті самі об'єкти ADO.NET.

Писати вручну виправдано, коли потрібен повний контроль: точні типи і розміри параметрів, потокове читання великих результатів, OUTPUT-параметри, специфічні можливості SqlClient.

**5. Чому конкатенація в SQL небезпечна, навіть якщо значення «просто Id»?**
- **Ін'єкція:** «Id» часто приходить рядком (з маршруту, JSON, заголовка), і `"1; DROP TABLE dbo.Bookings"` стане частиною команди.
- **Помилки на звичайних даних:** конкатенація ламається на апострофах (`O'Brien`), на форматах дат і десяткових чисел у різних культурах.
- **План виконання:** сервер не перевикористовує план, бо кожен текст запиту новий.

Параметри передаються окремо від тексту запиту, тому ніколи не виконуються як код.

**6. Як Unit of Work гарантує спільну транзакцію? Що, якщо репозиторій не отримає той самий SqlTransaction?**
UoW створює одне `SqlConnection` і передає всім репозиторіям делегат `() => _transaction`, тож кожна команда виконується з поточною транзакцією.

Якщо репозиторій виконає команду без неї на з'єднанні з активною транзакцією, SqlClient кине `InvalidOperationException`. Якщо ж у репозиторію своє окреме з'єднання, його зміни зафіксуються незалежно і не відкотяться разом з рештою — атомарність зламається.

**7. Як помилка процедури стає HTTP 409?**
1. `usp_Booking_ChangeStatus` виконує `THROW 50002`.
2. SqlClient кидає `SqlException`, `Number = 50002`.
3. `SqlErrorTranslator` у DAL перетворює його на `BusinessConflictException`.
4. Сервіс BLL відкочує транзакцію й прокидає виняток далі.
5. `DomainExceptionHandler` у API повертає 409 у форматі ProblemDetails.

**8. Навіщо два рівні валідації?**
- **DataAnnotations на DTO** дешево відсікають очевидно некоректні запити (формат email, діапазони) ще до сервісу і бази.
- **Бізнес-валідація в BLL** перевіряє правила, яким потрібен стан даних: чи існує клієнт, чи місце вільне, чи діє промокод. API про це знати не може.

**9. Optimistic vs pessimistic concurrency?**
- **Optimistic** (`rowversion`): конфлікт виявляється під час запису. Підходить, коли одночасні зміни рідкісні — як редагування профілю клієнта.
- **Pessimistic** (`UPDLOCK`): рядок блокується заздалегідь, і конфлікт неможливий. Підходить для частих одночасних записів — як зміна статусу бронювання касою, платіжним шлюзом і фоновою задачею.

**10. Чому 500 у відповідь на «не знайдено» — помилка проєктування?**
500 означає збій сервера. Клієнт не може відрізнити його від справжньої аварії: моніторинг піднімає тривогу, ретраї повторюють безнадійний запит. «Не знайдено» — нормальна, очікувана ситуація, і відповідь має бути 404 з поясненням.

**11. Навіщо Aspire AppHost уже зараз?**
Сервіс і його база запускаються однією командою з однаковою конфігурацією в кожного розробника. Рядки підключення передаються автоматично, а стан, логи й трасування видно в одному Dashboard. У Лаб. 05 до цього AppHost просто додадуться нові сервіси, Gateway й Aggregator.
