# Лаб. 03 — відповіді на контрольні питання

**1. Code-First vs Database-First.** У Code-First модель описується класами C# і Fluent API, а схему бази створюють міграції; у Database-First модель генерується з наявної бази (scaffold). Тут — Code-First: схема з Лаб. 01 відтворена конфігураціями `IEntityTypeConfiguration<T>`.

**2. Навіщо окремий клас конфігурації на сутність.** `DbContext` не розростається, кожна таблиця налаштовується в одному місці, а `ApplyConfigurationsFromAssembly` підключає всі конфігурації автоматично.

**3. Що таке міграція і що в ній зберігається.** Клас з методами `Up`/`Down` (зміни схеми) + `ModelSnapshot` — знімок моделі, з яким EF порівнює поточну модель при наступному `migrations add`. Застосовані міграції записуються в `__EFMigrationsHistory`.

**4. Навіщо SQL-скрипт міграції.** У продакшн схему зазвичай змінює DBA або конвеєр розгортання, а не застосунок. `--idempotent` дає скрипт, який можна безпечно запускати повторно.

**5. HasData vs програмний сідінг.** `HasData` — стабільні довідники з фіксованими ключами, потрапляють у міграцію. Програмний сідінг — тестові/залежні дані, які складно описати статично (зв'язки, дати); він має бути ідемпотентним (find-or-create).

**6. Eager, Explicit, Lazy Loading.** Eager — `Include/ThenInclude`, усе одним запитом (або split-запитами). Explicit — `Entry().Collection()/Reference().LoadAsync()`, окремий запит тоді, коли дані справді потрібні. Lazy — автоматично при зверненні до навігації (проксі), ризик N+1; у проєкті не використовується.

**7. Проблема N+1 і як її видно.** Один запит на список + по запиту на кожен елемент. Видно в лозі `Microsoft.EntityFrameworkCore.Database.Command`; лікується `Include`, проєкцією в DTO або split-запитом.

**8. AsNoTracking.** Для читання без змін: EF не створює знімків сутностей у ChangeTracker — менше пам'яті й швидше. Для сутностей, які змінюються й зберігаються, трекінг потрібен.

**9. Generic Repository і Unit of Work поверх EF.** `DbSet` вже є репозиторієм, а `DbContext` — UoW, але власні абстракції ховають EF від BLL, дають єдину точку для специфічних запитів і спрощують мокання в unit-тестах. Транзакція — один `SaveChangesAsync` в UoW.

**10. Чому пагінація має бути в SQL.** Інакше в пам'ять читаються всі рядки. `Skip/Take` на `IQueryable` перетворюється на `OFFSET … FETCH`; потрібне детерміноване сортування (тут — додатково `ThenBy(Id)`), а `totalCount` рахується окремим `COUNT` з тими самими фільтрами.

**11. DataAnnotations vs FluentValidation.** Атрибути — прості правила на самій DTO, перевіряються автоматично. FluentValidation — складні та перехресні правила, залежності (наприклад, `TimeProvider`), окремі тестовані класи.

**12. ProblemDetails.** Стандартний формат помилок HTTP API (RFC 9457): `type`, `title`, `status`, `detail`, `instance` + розширення (`traceId`, `errors`). Клієнт обробляє всі помилки однаково.

**13. Структуроване логування.** Повідомлення зберігає іменовані властивості (`{Method}`, `{Path}`), а не лише текст, тож логи можна фільтрувати й агрегувати. `CorrelationId` зв'язує всі записи одного запиту, включно з SQL-командами.

**14. Specification pattern.** Критерії, `Include`, сортування й пагінація інкапсульовані в об'єкті BLL, репозиторій лише застосовує специфікацію. Запити повторно використовуються, а логіку відбору можна тестувати без бази.

**15. Оптимістична конкурентність.** Стовпець `rowversion` (`IsRowVersion`) додається в `WHERE` при `UPDATE`; якщо рядок змінив хтось інший, EF кидає `DbUpdateConcurrencyException`, яку UoW перетворює на 409.
